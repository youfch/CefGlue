### 2. `ffmpeg_branding="Chrome"` vs `"Chromium"` 的区别

这两个 GN 构建标志控制着所有内容。以下是它们在 Chromium 官方文档中的定义：

**`ffmpeg_branding`**（来源：[chromium.org/audio-video](https://www.chromium.org/audio-video/)）：
- **`Chrome`** — 包含额外的专有编解码器（H.264、AAC、MP3 等），用于 Google Chrome。这些编解码器作为 **软件解码器** 内置于 FFmpeg 中。
- **`Chromium`**（默认）— 仅构建自由/开放编解码器集（VP8、VP9、AV1、Opus、Vorbis、FLAC）。

**`proprietary_codecs`**（来源：同上）：
- **`true`** — `<source>` 元素选择和 `canPlayType()` 报告支持专有编解码器。
- **`false`**（默认）— 浏览器表现得好像这些编解码器不存在。

这两个标志是相关联的：设置 `proprietary_codecs=true` 时，Chromium 的 `media/BUILD.gn` 包含一个断言，要求 `ffmpeg_branding != "Chromium"`。你*可以*通过补丁跳过该断言（参见下文第 5 节）。

来自 [Google Web Designer CEF 文档](https://support.google.com/webdesigner/answer/10043691) 的完整构建命令：

```bash
set GN_DEFINES=is_official_build=true proprietary_codecs=true ffmpeg_branding=Chrome
```

CEFSharp 的 **amaitland** 建议的完整命令行（来源：[CefSharp 讨论 #5090](https://github.com/cefsharp/CefSharp/discussions/5090)）：

```bash
set GN_DEFINES=is_official_build=true proprietary_codecs=true ffmpeg_branding=Chrome chrome_pgo_phase=0
set GN_ARGUMENTS=--ide=vs2022 --sln=cef --filters=//cef/*
```

### 3. 为什么 Spotify 构建不包含编解码器：许可问题

CEF 维护者 **magreenblatt** 在 [Issue #3559](https://github.com/chromiumembedded/cef/issues/3559) 中解释了原因：

> *"This is due to patent portfolio licensing requirements when using the FFmpeg library for software decoding of proprietary codecs (via the `ffmpeg_branding=Chrome` part). If you enable and distribute (via FFmpeg configuration) a software implementation of the patent protected technology as part of your application then you will likely be subject to said licensing requirements and associated costs."*

Chromium 的官方音频/视频页面将所有专有编解码器标记为 **"Limited to Google Chrome"**：
- H.264 / AVC
- H.265 / HEVC（需要硬件支持）
- AAC（Main、LC、HE 配置文件）
- MP3

---

### 4. 支持哪些编解码器 vs 不支持哪些（默认 CEF）

| 编解码器 | 默认 CEF (Spotify) | Chrome 品牌 CEF | 许可要求 |
|-----------|---------------------|--------------------|---------|
| VP8, VP9, AV1 | ✅ | ✅ | 免费 |
| Opus, Vorbis, FLAC | ✅ | ✅ | 免费 |
| **H.264 / AVC** | ❌ | ✅ | MPEG-LA 投资组合 |
| **H.265 / HEVC** | ❌ | ✅（需要硬件 + 补丁） | MPEG-LA + HEVC Advance |
| **AAC** | ❌ | ✅ | Via Licensing |
| **MP3** | ❌ | ✅ | 已过期（但构建系统中仍为“专有”） |

这意味着在默认的 CEF 构建中，YouTube 视频如果只有 H.264 格式则无法播放（许多直播和 60fps 视频会失败）。VP9/WebM 视频*可以*播放。来自 [Scali 的博客](https://scalibq.wordpress.com/2024/08/16/how-to-build-your-own-cef-with-mp4-support/)：

> *"With the standard build of CEF you can play some of the videos, but not all of them. Especially live streams and 50/60 fps content will often not work, because of unsupported codecs."*

### 5. 一种新兴替代方案：仅硬件解码（Issue #3559）

[Issue #3559](https://github.com/chromiumembedded/cef/issues/3559) 提出了一种方法，仅通过 Windows（Media Foundation）和 macOS（VideoToolbox）上的操作系统平台 API 启用硬件加速的 H.264 解码——*无需* `ffmpeg_branding=Chrome` 的软件解码部分。这将：

- 避免 FFmpeg 软件编解码器的许可义务
- 适用于具有硬件 H.264 解码器的现代 GPU
- **不**支持 AAC 音频解码（截至上次更新，该问题仍未解决）
- 对于旧的/被阻止列表的 GPU 会失败

该问题仍处于未解决状态（增强请求）。

### 6. 实用解决方案

**选项 A：自行构建 CEF（推荐）**
按照 [CEF 自动化构建设置指南](https://bitbucket.org/chromiumembedded/cef/wiki/AutomatedBuildSetup.md) 进行操作，并添加：

```bash
# Windows
set GN_DEFINES=is_official_build=true proprietary_codecs=true ffmpeg_branding=Chrome

# Linux/macOS
export GN_DEFINES="is_official_build=true proprietary_codecs=true ffmpeg_branding=Chrome"
```

然后只需将生成的 `libcef.dll` 和 `chrome_elf.dll`（Windows）替换到你的应用程序目录中。你不需要重建整个 CEF 封装器（如 CefSharp）。（来源：[Scali 的博客](https://scalibq.wordpress.com/2024/08/16/how-to-build-your-own-cef-with-mp4-support/)）

**选项 B：使用社区构建**
- [cefsharp/cef-binary](https://github.com/cefsharp/cef-binary/releases) 发布了 NuGet 重新打包（仍不带编解码器）
- [dsh0416/cef-automated-builds](https://github.com/dsh0416/cef-automated-builds) 提供了带有 `proprietary_codecs=true ffmpeg_branding=Chrome` 的 GitHub Actions 工作流以及额外的 H.265 补丁
- [nwjs-ffmpeg-prebuilt](https://github.com/nwjs-ffmpeg-prebuilt) 提供可以在某些配置下替换的 `ffmpeg.dll`

**选项 C：Linux 快捷方式（变通方案）**
一些用户从系统的 Chrome 安装中复制 `libffmpegsumo.so` 并将其放入 CEF 二进制目录。这利用了 Chrome 已启用的编解码器，跨版本*可能*有效。（来源：[CEF 论坛，主题 10741](https://www.magpcss.org/ceforum/viewtopic.php?f=6&t=10741)）

[![@magreenblatt](https://avatars.githubusercontent.com/u/413032?v=4&size=48)](https://github.com/magreenblatt)

Issue body actions

**Is your feature request related to a problem? Please describe.**  
By default, CEF/Chromium builds have proprietary codecs (H.264/AAC) disabled \[1\]. This is due to patent portfolio [licensing requirements](https://www.via-la.com/licensing/avc-h-264/) when using the FFmpeg library for software decoding of proprietary codecs (via the `ffmpeg_branding=Chrome` part). If you enable and distribute (via FFmpeg configuration) a software implementation of the patent protected technology as part of your application then you will likely be subject to said licensing requirements and associated costs.

\[1\] Proprietary codecs are marked as "Google Chrome only" at [https://www.chromium.org/audio-video/](https://www.chromium.org/audio-video/) and can generally be enabled by building CEF/Chromium with the `proprietary_codecs=true ffmpeg_branding=Chrome` GN arguments.

**Describe the solution you'd like**  
On Windows and MacOS, a (preferred) hardware video decoding path using OS platform APIs already exists in Chromium, and this implementation does not depend on configuring or distributing FFmpeg with software decoding of proprietary codecs enabled (leave out the `ffmpeg_branding=Chrome` part \[2\]). The OS manufacturers (Microsoft and Apple respectively) allow applications to use these OS platform APIs with no added licensing requirements or costs. We can consequently enable hardware-only support for proprietary video codecs (via OS platform APIs) with only minor changes to the existing CEF/Chromium build configuration.

\[2\] A small patch to disable the assert in [media/BUILD.gn](https://source.chromium.org/chromium/chromium/src/+/main:media/BUILD.gn;l=78?q=assert) is also required.

**Additional context**  
The problem with this approach is that devices lacking hardware decoding support will not be able to play proprietary codecs (due to the lack of software decoding support via FFmpeg). This is most likely to impact Windows users with old or blocklisted GPU hardware. This hardware-only configuration may still make sense for software developers/distributors who are minimally impacted by this population of older Windows hardware or who are otherwise willing to accept this licensing vs functionality trade-off.

**8/28/23 SUMMARY OF TEST RESULTS (M117)**

-   Chromium supports hardware h264 video decoding via OS APIs with minimal changes on Win/Mac.
-   Chromium does not (directly) support AAC audio decoding.
    -   FFmpeg on Mac should theoretically support AAC decoding via AudioToolbox, but we were unable to get it working.
    -   FFmpeg on Windows does not support decoding via Media Foundation (only encoding).
-   Chromium with `proprietary_codecs=true` includes additional (non-FFmpeg) proprietary code in //media that may potentially need to be replaced by OS APIs.

See related discussion below.

- **`Chrome`** — 包含额外的专有编解码器（H.264、AAC、MP3 等），用于 Google Chrome。这些编解码器作为 **软件解码器** 内置于 FFmpeg 中。
